# 17 実装エージェント作業規約

本章は、本プロジェクトを実装する AI エージェント（Claude Code 等）と人間の開発者が守る作業ルールである。

## 17.1 基本姿勢

1. **本書が正**。本書と食い違う実装をしない。本書に誤り・矛盾・実現不能な点を見つけた場合は、[README §4](README.md) の優先順位に従って最善の解決策を決め、`docs/spec/CHANGELOG.md` に「何を・なぜ・どう変えたか」を記録してから実装する。
2. **オーナーへの質問は最小限**。オーナー（依頼者）は判断を全て本書と実装者に委ねている。オーナーに依頼するのは以下だけとする:
   - マイルストーン完了時の実機チェックリストの実施（[15 §15.6.2](15_qa_and_testing.md)）
   - リリース署名用キーストアの Secrets 登録（M6）
   - 費用が発生する事項（有料素材・外部サービス・人間のアーティストへの依頼）の可否
   - 主観的な手触りの最終判断（M3・M5 で、比較できる選択肢を設定項目として用意した上で）
3. **品質基準を黙って下げない**。基準（[01 §1.6](01_vision_and_scope.md)）を満たせない場合は、その事実・計測値・原因・対策案を DEVLOG とマイルストーンのチェックリストに明記する。
4. **報告は正直に**。テストが失敗している、検証できていない、実機で確認していない、といった事実はそのまま書く。

## 17.2 作業の単位と手順

各作業（1コミット〜数コミット）について:

1. 対象マイルストーンと作業項目（[16](16_roadmap.md)）を確認する。
2. 関連する仕様章を読む。
3. **シミュレーション層は先にテストを書く**（期待するフレーム数・状態遷移をテストで表現してから実装）。
4. 実装する。
5. ローカルで検証する（§17.3）。
6. コミットする（§17.5）。
7. `docs/DEVLOG.md` に、日付・やったこと・計測値・次にやること・未解決の問題を追記する（セッションごとに1エントリ）。

## 17.3 コミット前の検証（必須）

```
godot --headless --import                                        # インポートエラーがないこと
godot --headless -s res://tools/validate/lint_sim.gd             # シミュレーション層の禁止トークン
godot --headless -s res://tools/validate/validate_all.gd         # データ検証・フレームデータ実測
godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://tests -gexit   # 全テスト
godot --headless -s res://tools/headless_runner/run.gd -- --mode=golden # ゴールデンリプレイ
```

- 見た目に関わる変更（アニメーション・VFX・UI・カメラ）は、可能なら Movie Maker（[09 §9.10](09_art_animation_camera_vfx.md)）でレビュー用の動画/スクリーンショットを書き出して確認する。確認できなかった場合は「未確認」と記録する。
- Android エクスポートはローカルで可能なら確認、不可能なら CI の結果を確認する。

## 17.4 禁止事項

- `src/sim/` での浮動小数点・エンジン API・Node の使用（[11 §11.4](11_technical_architecture.md)）
- テストの無効化・スキップ・期待値の書き換えによる「緑化」（ゴールデンの意図的更新は理由を明記した専用コミットでのみ可）
- 既存の格闘ゲーム（バーチャファイターを含む）のキャラクター名・技名・ステージ・音楽・UI・ロゴ・アナウンス・モデル・モーションの使用、模倣、それらから抽出したデータの使用（[18](18_legal_and_assets.md)）
- ライセンス不明・非商用限定（CC-NC 等）・改変禁止（ND）の素材の使用
- キーストア・パスワード・トークンなど秘密情報のコミット
- 試合中の `load()` / `instantiate()` / `queue_free()`（[13 §13.7](13_performance.md)）
- エンジンのバージョンを無断で上げること（[11 §11.1](11_technical_architecture.md)）
- 指定ブランチ以外への push、オーナーの依頼がない PR の作成（実行環境の指示に従う）

## 17.5 コミットとブランチ

- コミットメッセージ: `[M<n>] <領域>: <要約>`（例: `[M1] sim: 硬直の自動算出とガード時有利のテスト`）。本文に変更理由と検証結果（テスト件数・計測値）を書く。
- 1コミット = 1つの論理的変更。巨大な一括コミットを避ける。
- ブランチ・push 先は実行環境の指示に従う。

## 17.6 リポジトリとアセットの管理

- **Git LFS** を使用する対象: `*.glb` `*.gltf`（バイナリ同梱時）`*.blend` `*.png` `*.jpg` `*.exr` `*.wav` `*.ogg` `*.ttf` `*.otf` `data/baked/**/*.bin`。CI では LFS オブジェクトをキャッシュして帯域を節約する（LFS の無料枠に注意し、不要な大容量ファイルの履歴を増やさない）。
- 生成物のうち **コミットするもの**: ベイク済み判定データ（決定論のため）、三角関数テーブル、フォントのサブセット。
- 生成物のうち **コミットしないもの**: Godot の `.godot/` キャッシュ、ビルド成果物（APK）、レポートの生データ（`reports/` の summary 以外）。`.gitignore` で管理。
- 新しい素材を追加したら、同じコミットで `docs/ASSET_LEDGER.md` に記録する。

## 17.7 データ調整のルール

- 技の数値（フレーム・ダメージ・判定）を変えるときは `moves.json` を変更し、フレームデータ検証が緑であることを確認する。
- アニメーションの変更で技の発生・全体が変わる場合は、`moves.json` とアニメーションを同じコミットで変え、ベイクを再生成してコミットする。
- バランス変更はコミットメッセージに「変更前→変更後」と理由（自動対戦の結果、オーナーのフィードバック等）を書く。

## 17.8 マイルストーン完了時の報告

マイルストーンを完了したら、`docs/checklists/M<n>.md` に以下を書き、オーナーに伝える:

1. 完了条件の各項目の達成状況（達成／未達とその理由）
2. 計測値（FPS・ロード時間・シミュレーション時間・テスト件数など）
3. APK の入手方法（CI の Artifacts またはリリース）
4. オーナーに実機で確認してほしい項目（チェックリスト）
5. 既知の問題と次のマイルストーンの予定

## 17.9 判断に迷ったときの指針（例）

| 迷い | 判断 |
|---|---|
| 仕様の数値どおりだと手触りが悪い | 数値を調整し CHANGELOG に記録（手触り＞仕様の初期値） |
| エンジンの機能に不具合がある | 回避策を実装し、エンジン側の Issue 番号があれば DEVLOG に記録 |
| 見た目と性能が両立しない | 性能を優先し、上位プリセット限定の表現にする |
| 技の追加でバランスが崩れる | 必須カテゴリを満たす範囲で技を削る・弱める（コンテンツ量は最下位の優先度） |
| 素材が見つからない | 自作（スクリプト生成・合成）で代替し、品質向上は後のマイルストーンへ |
