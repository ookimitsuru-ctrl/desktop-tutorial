# 15 QA とテスト

## 15.1 テストの全体像

| 層 | 対象 | 実行場所 | 頻度 |
|---|---|---|---|
| 静的検査 | GDScript の型・警告、シミュレーション層の禁止トークン（[11 §11.4](11_technical_architecture.md)）、データスキーマ | CI | 全 push |
| 単体テスト | 固定小数点・三角関数・乱数・コマンドパーサー・状態遷移・判定・ダメージ計算 | CI（GUT） | 全 push |
| データテスト | 全技のフレームデータ実測、必須カテゴリ、参照整合、ベイク一致 | CI | 全 push |
| 結合テスト | シナリオ（2キャラ・入力列 → 期待結果） | CI（GUT） | 全 push |
| 決定論テスト | 同一入力の再実行・スナップショット往復・長時間ランダム入力 | CI | 全 push（短）/ 夜間（長） |
| ゴールデンリプレイ | 保存済みリプレイの最終チェックサム・勝敗の一致 | CI | 全 push |
| バランス | AI 自動対戦レポート | CI | 夜間 |
| 性能 | シミュレーション/AI ベンチマーク（CI）、実機フレームタイム | CI / 実機 | 夜間 / マイルストーン |
| 映像レビュー | Movie Maker による動画・スクリーンショット | CI / ローカル | 技・アニメ追加時 |
| 実機テスト | 操作感・表示・性能・サーマル・端末互換 | 実機（オーナー） | マイルストーンごと |

## 15.2 フレームデータの自動検証（Q6）

全キャラの全打撃技について、テスト用の「無限体力・行動なし」ダミーを相手に以下を自動実行し、**実測値**をデータと照合する。

1. **発生**: 技を入力したフレームから、攻撃判定が初めて出るフレームまでを数える → `startup` と一致
2. **持続**: 攻撃判定が出ているフレーム数 → `active` と一致
3. **全体**: 技開始から `actionable` が立つまで → `startup + active - 1 + recovery` と一致
4. **ガード時有利**: ダミーに立ち（またはしゃがみ）ガードさせて持続1F目に当たる距離で実行し、両者が行動可能になったフレームの差 → `on_block` と一致
5. **ヒット時有利 / CH 時有利**: 同様（CH は「ダミーが攻撃中」の状態を作って実行）→ `on_hit` / `on_ch` と一致（enum の場合はリアクションの種類が一致）
6. **段**: 立ちガード・しゃがみガード・無防備立ち・無防備しゃがみの4状態で、[02 §2.6.2](02_combat_system.md) の表どおりの結果になる
7. **追尾**: ダミーに奥回避・手前回避をさせ、回避成立区間での結果が `tracking` の定義どおりになる

- 投げについても、成立距離・抜け方向（正しい方向で抜けられる/違う方向では抜けられない）・ダメージ・投げ後の状態を検証する。
- 失敗したら、どの技のどの値がいくつ違うかをレポートし CI を失敗させる。
- トレーニングモードのフレーム表示も同じ「実測ロジック」を使う（表示と検証が同じコード）。

## 15.3 決定論テスト（Q7）

| テスト | 内容 | 規模（CI 通常 / 夜間） |
|---|---|---|
| 再実行一致 | 乱数入力（シード固定）で試合を実行し、全フレームのチェックサム列を記録 → 再実行して完全一致 | 10シード × 1万F / 100シード × 10万F |
| スナップショット往復 | 任意のフレームで `save_state` → 数十 F 進める → `load_state` → 同じ入力で進める → チェックサム一致 | 1,000 回 / 100,000 回 |
| ロールバック模擬 | 毎フレーム「1〜7F 前に巻き戻して再計算」しながら進め、巻き戻しなしの実行とチェックサム一致 | 1シード × 1万F / 20シード × 5万F |
| シリアライズ網羅 | `FighterState` / `WorldState` の全スクリプト変数がシリアライズに含まれている | 全 push |
| クロスプラットフォーム | x86_64（CI）で記録したゴールデンリプレイを、ARM 実機で再生してチェックサム一致（実機テスト項目） | マイルストーンごと |

## 15.4 ゴールデンリプレイ

- `tests/replays/` に代表的な試合のリプレイ（各キャラの全技を使う試合、リングアウト、壁破壊、タイムアップ、引き分けなど 30本以上）と、期待される最終チェックサム・勝敗を置く。
- ゲームルールやデータを **意図的に** 変更した場合は、`tools/update_golden.gd` で期待値を更新し、そのコミットで理由を説明する。意図しない変化はバグ。

## 15.5 単体・結合テストの必須項目（抜粋）

- 固定小数点: 乗除算の境界値、負数、`from_decimal_string`（"0.70"、"-1.25"、"0.0065" 等）
- 三角関数・atan2・sqrt: テーブル値の誤差 ≤ 1/65536 × 2
- コマンドパーサー: 全キャラの全コマンドの成立/不成立（猶予の境界 ±1F）、遡及同時押し、しゃがみ/手前回避の曖昧さ解決、優先順位
- ガード: 段×姿勢の全組み合わせ
- 回避: 直線/半回転/全回転 × 奥/手前 × 成立区間内外
- 投げ: 投げ間合い境界、しゃがみ・攻撃中・硬直中の投げられ不可、投げ抜けの方向と受付境界、投げ合い、多段投げ
- 浮き: 重力・再浮き減衰・強制落下（空中被弾 8）・補正率
- 壁・リングアウト: 各辺の種類 × 各状態、ガード押し戻しでリングアウトしない、柵の高さ判定、破壊壁の耐久
- ダウン: 受け身の受付境界、起き上がり各種、ダウン攻撃の当たり
- ラウンド: KO、タイムアップ（割合比較）、引き分け、延長、ダブル KO、PERFECT
- 入力: 1フレーム内の押下＋解放の検出、ラッチの消費、複数 Tick 処理時の扱い

## 15.6 実機テスト

### 15.6.1 テスト端末（最低構成）

| 区分 | 条件 |
|---|---|
| 最低ティア | 4GB RAM・Android 10〜12 の端末 1台 |
| 中ティア | 6GB RAM・Android 13〜14 の端末 1台 |
| 推奨ティア | ハイエンド・Android 14〜16、120Hz ディスプレイの端末 1台 |
| ゲームパッド | Xbox 系 1台、PlayStation 系 1台（Bluetooth） |

オーナーが所有する端末を優先する。足りない場合は Android エミュレータ（x86_64 ビルド）と、可能であればクラウドの実機テストサービスで補う。

### 15.6.2 マイルストーンごとの実機チェックリスト（オーナー向け）

各マイルストーンの完了時に、AI 実装者は以下のチェックリストを `docs/checklists/M<n>.md` として用意し、オーナーが実機で確認して結果を記入する。

- [ ] APK がインストールでき、起動する
- [ ] タイトル → 対戦まで操作できる（タッチ / ゲームパッド）
- [ ] 対戦中に引っかかり（カクつき）を感じない
- [ ] 画面右上（デバッグ時）の FPS 表示が 60 付近を維持する（10分間）
- [ ] タッチの同時押し（投げ）・回避（上下フリック）・ダッシュ（前2回）が狙い通りに出る
- [ ] 戻る操作でポーズになり、アプリが終了しない
- [ ] 着信・通知・アプリ切り替えから復帰してもクラッシュしない
- [ ] 音が遅れて聞こえない / 途切れない
- [ ] 30分遊んで端末が異常に熱くならない・FPS が落ちない（M5 以降）
- [ ] （自由記述）気になった点・手触りの感想

### 15.6.3 互換性テスト項目

- 画面比率（16:9、19.5:9、20:9、21:9、タブレット 4:3 / 16:10）での UI 配置
- ディスプレイカットアウト（パンチホール・ノッチ）回避
- ジェスチャーナビゲーション / 3ボタンナビゲーション
- 60Hz / 90Hz / 120Hz ディスプレイ
- Vulkan 非対応端末での GLES3 フォールバック（エミュレータで確認可）
- ゲームパッドの接続・切断（試合中を含む）
- 端末の言語（日本語 / 英語 / その他→英語）
- ストレージ空き容量不足時のセーブ失敗の扱い

## 15.7 バグ管理

- GitHub Issues を使う。ラベル: `bug` `crash` `perf` `balance` `feel`（手触り）`ui` `art` `audio` `data` `determinism`、重大度 `S1`〜`S4`。

| 重大度 | 定義 | 対応 |
|---|---|---|
| S1 | クラッシュ、進行不能、セーブ破損、決定論の破れ | 即時修正。他の作業を止める |
| S2 | 60fps を割る、入力の取りこぼし、ルールの誤り（フレームデータ不一致など） | 次の作業より優先 |
| S3 | 表示の不具合、軽微な操作性の問題 | マイルストーン内に修正 |
| S4 | 改善要望 | バックログ |

- バグ報告には、可能な限りリプレイファイル（`.rbr`）と状態ダンプ（F6）を添付する。決定論のおかげで、リプレイがあれば確実に再現できる。
