# 09 アート・アニメーション・カメラ・VFX

## 9.1 アートディレクション

### 9.1.1 方向性

**「スタイライズド・リアル」**: 実在の人間のプロポーションと武術の重みを保ちながら、形を大きな面で整理し、色と光で読みやすさを最大化する。

| 観点 | 方針 |
|---|---|
| プロポーション | 7.5頭身（実在よりわずかに英雄的）。手足の先（拳・足）を 5% 大きくして打撃の読みやすさを上げる |
| 形 | 筋肉・衣服のしわは大きな面で簡略化。細かいディテールはノーマルマップで |
| 色 | 各キャラに「主色1＋差し色1」。背景は低彩度、キャラは中〜高彩度 |
| 光 | 強いキーライト＋キャラ専用リムライトでシルエットを常に背景から分離 |
| 質感 | PBR ベースに、手描き風の色ムラと筆致をベースカラーに加える |
| 表情 | リアル寄り。誇張は気合・被弾・KO の瞬間のみ |
| 禁止 | 特定の既存ゲームの画面を想起させるルック（特定作品風のキャラデザイン、UI、ロゴ）の模倣 |

### 9.1.2 読みやすさのルール（必須）

- キャラクターと背景の輝度差: キャラのシルエット外周（リム）と、その背後の背景の平均輝度差 ≥ 20%（各ステージでスクリーンショット検証）。
- P1/P2 が同キャラ同色にならないよう、ミラー対戦時は 2P 側を自動的に別カラーにする。
- 攻撃中の手足は、カメラから見て胴体に隠れにくいポーズを優先（技の作成時のチェック項目）。

## 9.2 キャラクターモデル仕様

| 項目 | 仕様 |
|---|---|
| ポリゴン数（三角形） | LOD0: ≤ 28,000（High/Ultra・キャラ選択画面）、LOD1: ≤ 16,000（Medium）、LOD2: ≤ 9,000（Low） |
| スケルトン | Godot `SkeletonProfileHumanoid` 準拠の 56 ボーン（指を含む）＋ 揺れ物ボーン ≤ 24 ＋ 顔（顎・左右目）3 |
| 1頂点あたりのウェイト | ≤ 4 |
| マテリアル | ≤ 3（体・衣服 / 肌・顔 / 髪） |
| テクスチャ | ベースカラー、ノーマル、ORM（遮蔽・粗さ・金属）。2048²（High/Ultra）/ 1024²（Medium/Low、インポート時の縮小で生成） |
| 圧縮 | VRAM 圧縮（ETC2/ASTC）。ノーマルマップは法線用の設定 |
| ブレンドシェイプ | 7種: 通常、力み、被弾、叫び、KO（目閉じ）、笑み、まばたき（LOD0 のみ） |
| 基準姿勢 | 全キャラ共通の A ポーズ（腕 45°下げ）、ルートは両足の間の地面、+Z 方向が正面 |
| スケール | 1単位 = 1m、実寸 |
| ファイル | glTF 2.0 バイナリ（`.glb`）、`assets/characters/<id>/<id>_<costume>.glb` |

## 9.3 マテリアル・シェーダー・ライティング

### 9.3.1 キャラクターシェーダー（`shaders/character.gdshader`）

- ベース: 物理ベース（GGX スペキュラ）。
- **ラップライティング**: 拡散の明暗境界を `wrap = 0.3` で柔らかくし、境界付近に暖色の「疑似サブサーフェス」（肌のみ、強さはマテリアル毎）。
- **リムライト**: フレネル（`pow(1 - NdotV, 3.0)`）× ステージ定義の `rim_color` / `rim_intensity`（既定 0.6）。光源方向寄りを強くする（`rim_dir` を uniform で受け取る）。
- **ヒットフラッシュ**: 被弾時に 2F だけ白をわずかに加算（強さ 0.25、光過敏配慮 ON で 0.1）。
- **濡れ表現**: `wetness` uniform（雨のステージで 0.6）でラフネス低下・暗色化。
- **アウトライン**（任意・既定 OFF）: 反転ハルの `next_pass`（ビュー空間 1.2mm 相当）。Low では無効。
- カラーバリエーション: ベースカラーテクスチャに「カラーマスク」チャンネル（主色/差し色/第3色）を持たせ、色はシェーダー uniform で差し替える（カラー4種でテクスチャを増やさない）。

### 9.3.2 ステージのライティング

| 要素 | 仕様 |
|---|---|
| 平行光源 | 1灯（キー）。キャラクターのみリアルタイム影（プリセット依存）、ステージは LightmapGI にベイク済み |
| 環境光 | WorldEnvironment の空/環境色 ＋ ReflectionProbe 1つ（リング中心） |
| トーンマップ | AgX（エンジン対応版）。露出はステージごとに固定 |
| グロー | 有効（しきい値高め、強度控えめ）。Low では無効 |
| 色調整 | ステージごとのカラーグレーディング（3D LUT または調整パラメータ） |
| フォグ | 距離フォグ（必要なステージのみ） |
| 使わない | SSAO / SSR / SSIL / SDFGI / VoxelGI / ボリューメトリックフォグ（Mobile レンダラ非対応・高負荷のため） |

- Low プリセットのキャラ影は、足元への丸影デカール（`Decal`）で代替する。
- 壁・柵・背景物がカメラと被写体の間に入る場合、**ディザ透過でフェード** させる（壁マテリアルの共通シェーダー機能。カメラ→キャラの線分との距離で不透明度を決定）。

## 9.4 アセット制作パイプライン

### 9.4.1 方針

全てのアセットは **再現可能なスクリプトで生成・変換** できることを原則とする（AI 実装者がコンテナ内で作業でき、人間のアーティストが後から差し替えられる）。

```
[ベース人体（CC0）] ─┐
[衣装・髪・小物の生成スクリプト（Blender Python）] ─┼→ Blender（ヘッドレス）→ .glb（メッシュ＋スキン）
[テクスチャ生成/ベイク スクリプト] ─┘                      ↓
                                               Godot インポート（LOD生成・マテリアル割当・BoneMap）
[ポーズDSL（JSON）] → アニメーションビルダー（Godot ヘッドレス）→ AnimationLibrary（.res）
                                               ↓
                                     判定ベイカー（Godot ヘッドレス）→ data/baked/<id>/*.bin
```

### 9.4.2 ツール

| ツール | バージョン | 用途 |
|---|---|---|
| Blender | 4.x LTS（着手時の最新 LTS に固定） | モデル生成・衣装・テクスチャベイク・glTF 書き出し（`blender -b -P tools/blender/<script>.py`） |
| Godot エディタ（ヘッドレス） | 本体と同一 | インポート、アニメーションビルド、判定ベイク、テスト |
| ImageMagick / Python Pillow | 任意 | テクスチャの後処理、アイコン生成 |

### 9.4.3 キャラクターモデルの作り方（優先順）

1. **プランA（既定）**: CC0 ライセンスのベース人体（候補: MakeHuman / MPFB の CC0 出力、Quaternius などの CC0 ベースキャラクター）から、体型・顔のパラメータを調整して各キャラの素体を作る。衣装はスクリプトで素体の該当部位を複製・オフセット（Solidify / Shrinkwrap）して作成し、帯・バンテージ・ベルト等はカーブから生成。髪はカード＋シェル（揺れ物ボーン付き）。テクスチャは Blender のプロシージャルシェーダーからベイクし、筆致ノイズを重ねる。
2. **プランB（品質向上）**: 人間のアーティストによる制作、または商用利用可能な規約の 3D 生成ツールで作ったモデルを、**同じスケルトン規約（§9.2）にリトポ・リグ** して差し替える。
- どちらのプランでも、スケルトン・基準姿勢・ファイル名・マテリアルスロットの規約を守れば、アニメーション・判定データはそのまま使える（差し替え可能性の保証）。
- 採用した全ての素材は [18 法務](18_legal_and_assets.md) のアセット台帳に記録する。

### 9.4.4 Godot インポート設定

- `.glb` のインポートスクリプト（`tools/import/character_post_import.gd`）で: BoneMap による `SkeletonProfileHumanoid` へのリターゲット、LOD 生成、影用メッシュ生成、キャラクターシェーダーのマテリアル割当、揺れ物ボーンへの `SpringBoneSimulator3D` 設定を自動で行う。
- 手作業のインポート設定変更は禁止（全てスクリプトか `.import` ファイルの差分としてリポジトリに残す）。

## 9.5 アニメーション

### 9.5.1 必要なアニメーション

| 区分 | 数（1キャラあたり） | 共有 |
|---|---|---|
| 技（攻撃・投げの攻撃側・構え） | 60〜80 | キャラ固有 |
| 被投げ（投げられ側） | 投げ1つにつき1 | **投げる側のキャラのデータとして作り、全キャラ共通の標準骨格で再生**（体格差は位置補正と IK で吸収） |
| 移動・ガード・しゃがみ・回避・ダッシュ・走り | 約20 | キャラ固有（構えの個性が出るため） |
| 被弾リアクション（§02 2.7.4 の全種、左右・強弱） | 約30 | **共通セットを1つ作り全キャラで共有**。キャラ別に上書き可 |
| ダウン・受け身・起き上がり（4向き × 種類） | 約30 | 共通セット＋キャラ別の起き上がり攻撃 |
| 登場・勝利×3・敗北・KO 落下×3・リングアウト落下 | 約10 | キャラ固有（落下は共通） |

### 9.5.2 ポーズDSL（アニメーションの記述形式）

AI 実装者が数値で直接アニメーションを書けるよう、**キーポーズ＋補間** の JSON 形式を定義する（スキーマ: [12 §12.5](12_data_formats.md)）。

- 60fps 基準のフレーム番号でキーを置く。キーごとにボーン回転（基準姿勢からのオイラー角、度）・ルート位置（m）・イージングを指定。
- **ポーズライブラリ**: 名前付きポーズ（例: `toma.stance`、`common.fist_extended_r`）を定義し、キーは「ベースポーズ＋差分」で書ける。
- **ミラー**: 左右反転したアニメーションを自動生成できる。
- ビルダーは全フレーム（60fps）をベイクした `Animation` リソースを出力する（補間の解釈差をなくすため、実行時の補間に頼らない）。
- **ルートモーション（移動）の唯一の正はアニメーション** である。ビルダーはルートの移動量をフレームごとに抽出し、固定小数点の移動カーブとして `data/baked/<id>/motion.bin` に出力する。シミュレーションはこのカーブで移動し、描画側はアニメーションをその場再生（ルート固定）してモデルをシミュレーション位置に置く（＝足滑りが原理的に起きない）。

### 9.5.3 格闘ゲームのアニメーション制作ルール（必須）

| ルール | 内容 |
|---|---|
| 発生フレームの一致 | 打撃の「当たる瞬間のポーズ（最大伸展）」は、技データの発生フレームに必ず置く。ビルダーが `contact_frame` と `startup` の一致を検証する |
| 予備動作 | 発生までの最初の 30〜40% で予備動作（溜め）を見せ、発生直前の 2〜4F で一気に加速（イーズイン）する |
| 持続 | 持続中は伸展ポーズをわずかに保持し、1〜2F のオーバーシュート |
| 硬直 | 硬直は「隙がある」と見て分かる戻り（スナップバックしない）。イーズアウト＋フォロースルー |
| 重心 | 腰が先行し肩が 1〜2F 遅れて追従。踏み込みのある技は軸足を地面に固定 |
| 段の読みやすさ | 下段は最初に明確な沈み込み、中段は胴体の前傾、上段は肩・腰の高い回転 |
| 全体フレーム一致 | アニメーションの長さ = 技の全体フレーム。違えばビルドエラー |
| 構え | 待機はキャラの流派が一目で分かる構え。2〜3秒周期の呼吸ループ |
| 被弾 | 被弾の最初の 2F で大きく動かし（衝撃）、残りで減衰。ヒット方向（左右）で反転版を使う |

### 9.5.4 再生方式（フレームロック）

- 各キャラの `AnimationTree` は **手動更新モード**（`callback_mode_process = MANUAL`）とし、毎描画フレーム、シミュレーション状態（状態ID・技ID・状態内フレーム）から「どのアニメーションの何フレーム目か」を決めて **シーク** する。描画は常にシミュレーションの現在フレームと一致する。
- 遷移ブレンド: 直前の表示ポーズから新しいアニメーションへのクロスフェード。

| 遷移先 | クロスフェード |
|---|---|
| 攻撃技（待機・歩きから） | 2F |
| 攻撃技（連携の次段） | 0F（次段のアニメーションは前段の終わりから繋がるように作る） |
| 被弾リアクション | 2F |
| ガード硬直 | 1F |
| 待機・歩き・しゃがみ | 4F |
| 投げ（攻撃側・被投げ側） | 2F |

- ヒットストップ中はアニメーションのシーク位置を止める（＝止まる）。わずかな振動（被弾側のみ、ボーンにノイズ加算 2mm）で「止まっているが生きている」感を出す。

### 9.5.5 手続き的レイヤー（描画のみ・シミュレーションに影響しない）

| レイヤー | 実装 | 内容 |
|---|---|---|
| 揺れ物 | `SpringBoneSimulator3D` | 髪・帯・衣服の裾・バンダナ。巻き戻し（ロールバック）や瞬間移動時はリセット |
| 視線 | `LookAtModifier3D`（または自前の SkeletonModifier3D） | 待機・歩き・ガード中に頭と目が相手を追う（最大 30°）。攻撃中は無効 |
| 足の接地 | 自前の 2ボーン IK（SkeletonModifier3D） | 床は平面だが、筏ステージの傾き（見た目）に足を合わせる |
| 被弾の加算 | 加算ポーズ | 重い被弾で被弾方向へ上体を 6F 揺らす |
| 表情 | ブレンドシェイプ | イベント駆動（攻撃=力み、被弾=被弾、KO=目閉じ、勝利=笑み、ランダムまばたき） |

## 9.6 判定のベイク

- `tools/bake/bake_boxes.gd`（Godot ヘッドレス）で、各キャラの全アニメーションを 60fps で 1F ずつシークし、ボーンのグローバル姿勢から **喰らい判定カプセル 11本** と **攻撃判定**（技データが指定するボーン＋オフセット＋半径）の位置を計算する。
- 座標はキャラのローカル空間（ルート基準・+Z 正面）で Q16.16 整数に変換し、`data/baked/<id>/hurt.bin`、`hit.bin`、`motion.bin` とインデックス `index.json` に出力する。
- **ベイク結果はリポジトリにコミット** する（実行環境による浮動小数点の差がシミュレーションに入らないようにするため）。CI は再ベイクしてコミット済みのものと一致することを確認し、不一致ならビルドを失敗させる（アニメーション変更時はベイクのコミット漏れになる）。

| 喰らい判定 | ボーン（始点→終点） | 半径 |
|---|---|---|
| 頭 | Head 中心（球） | 0.11m |
| 胸 | UpperChest → Neck | 0.16m |
| 腹 | Hips → Spine | 0.15m |
| 上腕 L/R | UpperArm → LowerArm | 0.055m |
| 前腕 L/R | LowerArm → Hand | 0.05m |
| 大腿 L/R | UpperLeg → LowerLeg | 0.08m |
| 下腿 L/R | LowerLeg → Foot | 0.06m |

- キャラの体格差に合わせ、半径はキャラ別の倍率を `character.json` で指定できる（例: ビョルン ×1.15）。

## 9.7 投げのペアアニメーション

- 投げアニメーションは、攻撃側のアニメーションと、被投げ側のアニメーション（標準骨格）と、**被投げ側のルートの相対変換トラック**（攻撃側ルート基準）の3つで1組とする。
- シミュレーションは相対変換トラックのベイク結果（固定小数点）に従って被投げ側を配置する。投げ終了時の位置・向き・ダウン状態はデータで定義する。
- 描画では、攻撃側の手と被投げ側の掴まれる部位を IK で合わせる（体格差の吸収、任意）。
- 大技の投げ（`cinematic: true`）のみ、専用カメラ（§9.8.4）を使ってよい。

## 9.8 カメラ

### 9.8.1 基本原理

- カメラは常に **対戦軸に垂直な方向** から両者を見る（横から見る）。
- 対戦軸の「どちら側」にカメラがいるか（`cam_dir`）は **シミュレーション状態** として決定論的に更新する（入力の左右解釈に使うため。[03 §3.5.3](03_controls_and_input.md)）:
  ```
  perp = rotate90(対戦軸の単位ベクトル)
  if dot(perp, cam_dir_prev) < 0: perp = -perp
  cam_dir = perp
  ```
  これにより、横移動で回り込んでもカメラが追従して画面の左右関係は保たれ、**投げによる位置入れ替えなどで対戦軸が瞬時に反転したときだけ** 画面上の左右が入れ替わる。
- オプション「1P を常に左に」（オフライン1P時のみ）: 左右が入れ替わった場合、カメラが 40F かけて 180° 回り込み、`cam_dir` も反転する。

### 9.8.2 通常カメラのパラメータ

| 項目 | 値 |
|---|---|
| 注視点 | 両者の中間点。高さ 0.95m。空中の相手がいる場合はその高さの 40% を加算 |
| 垂直画角 | 32° |
| 距離 | 両者の外側に各 0.9m の余白を含めて水平方向に収まる距離。範囲 3.6〜8.0m |
| カメラ高さ | 1.25m ＋ (距離 − 3.6m) × 0.15 |
| 平滑化 | 臨界減衰スプリング。位置の半減期 0.10秒、ヨーの半減期 0.12秒、最大ヨー速度 180°/秒 |
| 画面比率 | 16:9〜22:9 で同じ見え方（垂直画角固定・距離で水平を確保）。4:3 タブレットでは距離が伸びる |

### 9.8.3 カメラの揺れ

- 「トラウマ」モデル: 被弾で trauma を加算（light 0.15 / medium 0.25 / heavy 0.4 / CH +0.15 / 壁 0.5 / KO 0.6）、揺れ量 = trauma² × 最大振幅（位置 3cm・回転 0.6°）、毎秒 1.5 減衰。
- 設定の「カメラ揺れ」倍率を掛ける。

### 9.8.4 特殊カメラ（全て描画のみ・シミュレーション非依存）

| 場面 | 動き | 長さ |
|---|---|---|
| ラウンド開始（1R目） | ステージ別のスプライン（全景→2人へ寄る） | 2.5秒 |
| 大技の投げ（`cinematic`） | わずかに回り込み＋10% ズームイン、終了時に通常へ戻る | ≤ 50F |
| 浮かせ | 注視点を空中の相手へ寄せる（上記 40%） | — |
| 壁ヒット | 壁側へわずかに寄る＋揺れ | 20F |
| リングアウト | カメラ位置を固定し、落下するキャラを注視（パン） | 1.5秒 |
| KO | 0.35倍速スロー（45F）、KO した打撃の瞬間に寄る | 45F |
| KOリプレイ | 自動ディレクター（6種のショットから選択: ローアングル、肩越し、回り込み、真横、俯瞰、クローズアップ）。ヒットの瞬間を含むようにショットを切り替え | 4秒 |
| 勝利ポーズ | 勝者の周りを回り込み、正面で止まる | 2.5秒 |

## 9.9 VFX（エフェクト）

### 9.9.1 一覧

|---|---|---|---|
| `hit_light` / `hit_medium` / `hit_heavy` | HitConfirmed | 接触点に放射状の光条＋フリップブックの閃光（白〜黄）。強さで大きさ・光条数を変える | 8〜14F |
| `hit_counter` | HitConfirmed(CH) | 朱色の閃光＋衝撃波リング。通常の 1.3倍 | 14F |
| `guard_spark` | Blocked | 青白の弧（防御側の前面に盾形）＋小さな火花 | 8F |
| `evade_ghost` | EvadeSucceeded | 回避した側の残像（半透明の簡易シェーダーで2体、0.1秒間隔） | 18F |
| `throw_break` | ThrowEscaped / ThrowClash | 2人の間に白いリング | 12F |
| `limb_trail` | （v1.4 で廃止） | — | — |
| `dust_step` / `dust_land` | ダッシュ・着地・ダウン | 床の土煙（ステージ材質で色を変える: 砂、雪、水しぶき、木屑） | 20〜40F |

### 9.9.2 実装ルール

- 全エフェクトはオブジェクトプールから再利用（試合中に `instantiate()` しない）。試合開始前に全種をプリウォーム。
- パーティクルは `GPUParticles3D`（Compatibility レンダラでも動作する機能のみ使用）。
- エフェクトはシミュレーションのイベントで発生させる。オンライン（ロールバック）時のための「同一イベントの重複発生防止」（イベントの `(frame, kind, player, move_id)` で重複排除）を最初から入れておく。
- 品質プリセットごとの上限（[13 §13.3](13_performance.md)）を超える場合は優先度の低いもの（土煙等）から間引く。

## 9.10 映像レビュー（実機なしでの品質確認）

- Godot の **Movie Maker モード** を使い、リプレイファイルから決定論的に動画を書き出すツールを用意する:
  `godot --path . --write-movie out/review.avi --fixed-fps 60 res://tools/review/review.tscn -- --replay=res://tests/replays/<name>.rbr --camera=auto`
- 新しい技・アニメーションを追加したら、該当技を実演するリプレイから動画を書き出し、フレーム単位でポーズ・判定表示・エフェクトを確認する（判定表示 ON 版も書き出す）。
- 各ステージの代表スクリーンショット（4方向 × 2キャラ組み合わせ）を CI で生成し、読みやすさルール（§9.1.2）の輝度差を自動計測する。
